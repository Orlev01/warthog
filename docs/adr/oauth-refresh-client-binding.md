# Persist the issuing client on OAuth tokens

Date: 2026-11-11. Status: accepted for the security bug bash.

Authorization codes already retain the client identity validated during authorization, but the old token schema retained only the agent connection. Refresh therefore ignored the submitted client ID. Store the validated `authCode.clientId` on every new access/refresh token and carry it unchanged through rotation and retry grace. Require the exact client ID before retiring a token, minting a successor or applying replay revocation. A replay revokes that client's tokens on the connection; explicit connection revocation/disconnection still removes all clients' tokens and pending authorization codes. Cleanup retains replay evidence per connection and client.

CIMD clients may be resolved from validated HTTPS metadata without a persisted `oauth_clients` row, so the new column is not a foreign key to the DCR registry. A public client ID is not sender authentication; this change preserves the authorization grant's client binding and prevents mismatched requests from rotating or revoking another client's tokens. It does not make a stolen bearer safe. [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

Migration `0105_oauth_token_client_binding.sql` adds a nullable `oauth_tokens.client_id` column. No safe historical backfill exists: consumed authorization-code rows are deleted, pending authorizations are transient, and agent name/platform fields are display metadata. Even an outstanding authorization code for the same connection cannot establish an existing token's original client. Existing rows therefore remain `NULL`.

An unbound legacy refresh token returns `invalid_grant` without minting, retiring or revoking other tokens. Its client must complete authorization once again. Existing access tokens keep their original expiry and verification behavior; static access keys and service-provider connector credentials are unaffected. The migration itself does not delete tokens or disconnect agents. The current consent flow creates a new agent connection on reauthorization; it does not infer or copy the previous connection's custom grants. Review the new consent permissions, reapply any custom agent settings as needed, and disconnect the obsolete entry after the replacement works. Historical activity remains attached to its original agent.

Deployment must apply the additive migration before starting the new runtime; the normal migration runner does this under its migration role. Runtime and purge table privileges already cover the added column. The migration leaves existing credential values and expiries unchanged and is recorded by the normal migration ledger. Rollback to the previous runtime is schema compatible because old inserts can omit the nullable column. Retain the column on rollback: dropping it would discard newly recorded bindings. An old-runtime rollback also restores the original missing-binding behavior and can issue new unbound tokens, which again require authorization after the fixed runtime returns; prefer a forward correction where possible.

Coverage includes a pre-migration fixture upgraded through the real migration runner, unbound refresh rejection with unchanged legacy access behavior, exact/missing/mismatched client IDs, code exchange, rotation/grace, rollback, revocation races, multiple clients sharing a connection, and a dynamically validated CIMD identity. The local PostgreSQL16 certification harness additionally observes real lock waiters for wrong-client refresh versus rotation and for recovery-code regeneration versus passkey registration in both orders. That harness is executed by the integration owner, not by this isolated review agent.
